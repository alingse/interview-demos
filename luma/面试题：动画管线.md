# 数据工程实战题：动画元数据的增量处理与跨源匹配 Pipeline

## 背景

团队需要建设一个持续运行的数据处理服务：定期从上游数据源获取新增的动画/漫画元数据，进行质量检查，与 Wikidata 知识库进行匹配对齐，将匹配结果存入本地数据库，并支持按需导出。

整个流程需要支持增量处理（只处理新增数据）和断点恢复（中途失败后能从断点继续），因为这是一个需要长期、反复运行的服务。

## 数据源

### A. 上游数据 —— MyAnimeList (MAL) 动画元数据

- Kaggle 上有多个 MAL 数据集（搜索 "myanimelist dataset"），包含约 2 万+ 动画条目，含标题（日文/英文/罗马字）、类型、集数、评分、年份、制作公司等字段
- 也可通过 Jikan API（MAL 的免费非官方 REST API：https://docs.jikan.moe/）分页获取数据
- 两种数据获取方式任选；如用 Kaggle 静态数据集，可按年份或 ID 范围分批加载来模拟"增量到达"

### B. 知识库 —— Wikidata

- Wikidata 中有大量动画相关实体，含多语言标签和外部标识符
- 获取方式：SPARQL 查询（https://query.wikidata.org/）或 HuggingFace 数据集
- 提示：探索 Wikidata 中与 MAL 相关的属性和标识符，这对匹配策略和 pipeline 设计都很重要

## 任务

### 1. 设计并实现端到端的增量数据处理 pipeline，包含以下环节：

**a. 数据获取**
- 从 MAL 数据源获取动画元数据
- 支持增量：记录已处理的范围，下次运行只获取新增部分
- 如使用 API：处理分页、限流；如使用静态数据集：设计分批加载策略模拟增量

**b. 质量检查**
- 定义并实现至少 3 条数据质量检查规则（如字段完整性、格式合法性、值域范围、重复检测等）
- 不合格数据单独记录，不阻塞整体流程

**c. 跨源匹配**
- 将通过质量检查的 MAL 条目与 Wikidata 实体进行匹配
- 至少实现一种高置信度匹配 + 一种模糊匹配
- 记录匹配方式和置信度

**d. 结果存储**
- 匹配结果存入本地数据库（SQLite 即可）
- schema 设计应区分：已匹配、未匹配、低置信度待审查
- 支持增量写入：新一轮处理结果追加到已有数据上

**e. 断点恢复**
- pipeline 中途中断后（网络断开、程序崩溃等），重启能从中断处继续，不重复处理已完成的数据
- 考虑：获取了但还没匹配的、匹配了但还没写库的——各阶段的中间状态如何处理

**f. 数据导出**
- 支持按需导出为 JSON Lines 格式
- 导出内容包含：MAL 元数据、Wikidata 元数据、匹配关系、置信度

### 2. 每次运行输出处理报告

- 本轮：新增数量、质量检查通过/未通过、匹配/未匹配
- 累计：总处理数、总匹配率、各置信度区间分布

### 3. 在文档中说明

- pipeline 整体架构和各环节职责划分
- checkpoint 设计：存什么状态、存在哪、如何保证幂等性
- 你如何测试了断点恢复功能（模拟了什么故障、恢复后的行为是否符合预期）
- 如果要将这个 pipeline 部署为长期运行的生产服务，还需要考虑什么

## 验收场景

我们会 clone 你的 repo，运行 pipeline 处理前 1000 条数据，在匹配阶段 kill 进程，然后重启 pipeline——期望它能从断点继续处理，而不是从头开始。请确保你的代码支持这个场景。

## 考察方向的优先级（从高到低）

1. 增量和断点恢复设计（最核心）
2. pipeline 整体架构的清晰度
3. 工程取舍与代码质量
4. 跨源匹配策略
5. 生产化思考

## 架构扩展问题（在文档中回答）

如果 MAL 数据源从 2 万条变成 200 万条，你的设计哪些地方需要改？怎么改？

## 要求

- 必须使用 AI 工具（ChatGPT / Claude / Kimi / 通义 / Cursor 等均可），提交 AI 对话记录（至少包含所有 prompt；含回答更好但不强制）
- 需要独立完成，可以使用 AI，但不能让其他人协助或代做
- 使用 git 管理代码，要求有意义的 commit message，能体现开发过程，不接受单次大提交。commit 频率应与 AI 对话记录的时间线大致对应
- 交付物：包含 .git/ 的完整项目目录（打包或 git repo 链接均可） + 文档（架构设计、checkpoint 策略、断点恢复测试、取舍决策、已知局限、架构扩展讨论） + AI 对话记录
- 如有疑问可以提问

## 时间与完成度

- 建议 1–2 周内提交。如果希望多花时间打磨以获得更好的结果，也可以
- 不要求全部完成——我们更看重整个处理过程、思路和方案设计：遇到问题时如何分析、做了哪些取舍、为什么选择这个方案。当然，如果能有较好的结果是加分项

## 说明

- 数据规模：用几千到 2 万条 MAL 数据即可，个人电脑可处理
- 如使用 Jikan API，注意免费额度限制（每秒 3 次请求）；也可直接下载 Kaggle 数据集避免 API 限制
- 数据库用 SQLite 即可，不需要部署独立数据库服务
- 如果某个数据源访问不便，说明情况并尝试替代方案，不影响评估
